# RA-001 — Inference service boundaries and reproducible hosts

**Research article · Version 0.1 · Published 2026-11-11 (America/New_York) · Not peer reviewed**

**Type:** Research synthesis and methods proposal. **Review stage:** Initial critical synthesis. **Data status:** No new empirical dataset or result; proposed comparisons are unrun.

## Research question and argument

A reproducible inference experiment begins by identifying where the model executes. A Linux program that calls a hosted service, a local model server, and a training job have different resource boundaries. Installing a client library does not install the weights of the hosted model. Resource claims should name the measured boundary before offering a minimum RAM or GPU requirement.

## Evidence and limits

[OpenAI](REFERENCES.md#openai) documents a service API, authentication, request identifiers, and versioning considerations. It supports studying request provenance. It supplies no universal local hardware specification for every model accessible through that API. Historical installation fragments also require current dependency checks before they can serve as reproducible methods.

## Proposed comparison

1. Define the task, execution boundary, model revision, client version, and complete input before measuring.
2. Compare a hosted-service client and a stated local-model configuration only where task and scoring are comparable; disclose differences in the actual models.
3. Measure client memory, local server memory, preprocessing, transfer, latency, failures, and external service cost in separate columns.
4. Repeat with cold and warm process state, fixed concurrency, and a documented caching policy.
5. Retain configuration manifests without embedding credentials, default passwords, or machine-specific access details.

## Data needed to assess the claim

| Record | Purpose |
| --- | --- |
| Execution boundary | Which component was measured and which was external |
| Request and input identity | Exact request content and result ancestry |
| Model/client revisions | What could have changed between runs |
| Resource interval | Start, end, concurrency, warmup, and accounting scope |
| Failure outcome | Timeout, refusal, unavailable service, or incorrect result |

## Interpretation and failure criteria

A smaller client footprint does not establish a cheaper complete inference task. A successful response establishes request completion; its correctness needs an independent task score. No installation script or operating-system cleanup sequence is validated by this article.

**Vocabulary — Execution boundary: the explicit set of components included in a measurement.**
