# RA-004 — Behavioral evidence for generated and transformed code

**Research article · Version 0.1 · Published 2026-11-11 (America/New_York) · Not peer reviewed**

**Type:** Research synthesis and methods proposal. **Review stage:** Initial critical synthesis. **Data status:** No new empirical dataset or result; proposed comparisons are unrun.

## Research question and argument

Generated text, a valid program representation, a successful build, and a useful behavior are distinct observations. Evolutionary code generation becomes research when the candidate population, selection rule, execution boundary, and fitness measurement can be inspected. Compilation success alone is an inadequate fitness objective for claims about useful adaptation.

## Evidence and limits

[LLVM project](REFERENCES.md#llvm) provides a specified intermediate representation and validity rules. [Ofria and Wilke, 2004](REFERENCES.md#avida) provides a precedent for controlled experiments with evolving programs. Neither establishes that arbitrary generated C++ fragments acquire useful behavior, persistence, or consciousness.

## Proposed comparison

1. Define the permitted program representation, mutation operators, resource limits, and fixed task population.
2. Compare unchanged programs, random variation, and feedback-guided variation under equal evaluation budgets.
3. Separate parse, verification, build, execution, task-correctness, and invariant failures in the outcome record.
4. Evaluate accepted candidates on a held-out task set and preserve rejected candidates in the denominator.
5. Treat a competitive shared-memory game as a specified simulator; results there require a separate argument before transfer to an operating system.

## Data needed to assess the claim

| Record | Purpose |
| --- | --- |
| Candidate parent | Which artifact was varied |
| Transformation identity | Generator, mutation, compiler, and build revision |
| Evaluation exposure | All attempted candidates and consumed resources |
| Behavioral outcome | Task score, invariant violations, and runtime failures |
| Selection decision | Why a candidate was accepted or rejected |

## Interpretation and failure criteria

Reject an improvement claim if gains depend on extra search budget, changed tests, or disappearance of failed candidates. Code validity and resource containment are necessary checks but do not substitute for a behavioral comparison.

**Vocabulary — Fitness function: the explicit rule that scores a candidate for selection.**
