# RA-005 — Computational reproduction and bounded inheritance

**Research article · Version 0.3 · Expanded 2026-11-13 (America/New_York) · Not peer reviewed**

**Type:** Research synthesis and methods proposal. **Review stage:** Initial critical synthesis. **Data status:** No new empirical dataset or result; proposed comparisons are unrun.

**Editorial provenance:** Version 0.2 teaching additions were prepared with AI assistance from the already released paper, notes and public terminology; the proposed framework and original article remain attributed to Mark Yarian.

## Research question and argument

A computational descendant needs a stated parent, an inherited-state boundary, and an independently testable continuity criterion. Copying files, migrating a process, adapting a model, and producing a separately executing descendant should be recorded as distinct operations. Their biological resemblance is a research motivation rather than an outcome label.

## Evidence and limits

[Ofria and Wilke, 2004](REFERENCES.md#avida) establishes an experimental setting for evolving, self-replicating programs. The published Digital Mitosis paper proposes a separate engineering framework. Evidence for the platform does not independently validate that proposed framework or a particular digital-cell implementation.

## Proposed comparison

1. Specify inherited executable configuration, memory, model state, identity records, limits, and excluded external state.
2. Compare a fresh installation, an ordinary clone, checkpoint migration, and a bounded-variation descendant.
3. Test independent restart, retained tasks, changed inputs, and corrupted inheritance partitions.
4. Measure behavioral continuity and novel task behavior separately using held-out tasks.
5. Preserve lineage and resource use for unsuccessful descendants as well as successful ones.

## Interpretation and failure criteria

A restartable clone supports a bounded continuity claim, not a claim of biological life. An adaptation advantage must survive cloning controls, matched resources, and held-out evaluation. No reproduction trial is reported in this article.

## A worked technical comparison

The [lineage lab](../public-experiments/lineage-lab/README.md) provides a small Python example using a parent with weight `2` and one memory entry. A faithful child inherits both and receives a separate identity. A second child receives an explicitly bounded change to its weight. The code evaluates both on three fixed inputs and records the parent, child and checksums.

The case is deliberately easy to falsify. At input `0`, the changed child's output equals the parent's; at input `5`, it differs. One matching response therefore cannot identify ancestry or prove unchanged behavior. Dropping a memory item breaks the stored checksum, while an unrecorded change outside the declared budget is rejected. The checksum demonstrates local snapshot consistency; it cannot authenticate who created the record.

| Claim | Test that would support it | A failure or narrower interpretation |
| --- | --- | --- |
| A new child exists | Separate child ID, declared parent, explicit division event | A second process with shared files alone could be an ordinary clone |
| Chosen state survived | Compare declared parent and child snapshots | A similar output may hide different memory or configuration |
| Variation stayed bounded | Compare change record against a declared budget | An unrecorded change defeats the stated inheritance claim |
| Behavior persisted | Repeat on held-out tasks with matched resources | One favorable example or extra attempts overstates continuity |
| A population improved | Count every eligible descendant, failure and cost | Selecting only the best survivor biases the result |

This exercise illustrates experimental design; it is not a Digital Mitosis implementation or an empirical result about a new computational organism. The [terminology crosswalk](../docs/TERMINOLOGY_CROSSWALK.md) connects Digital Cell, Symbolic Genome and Mutation Governance to these narrower measurements.

**Vocabulary — Inheritance partition: the declared portion of a parent state transferred to a descendant.**

## Historical cluster case study and proposed experiment

**Evidence status (2026-11-13):** This section summarizes preserved historical source and JSON observations, not a new controlled experiment. Reported counters are retrospective system records, not independently reproduced experimental results. The [historical evidence ledger](HISTORICAL_CLUSTER_EVIDENCE.md) gives the shared provenance and publication limits.

Two historical designs are relevant without constituting a reproduction result. ContinuityNode 0.5.0 separated persistent lineage identity, runtime sensing, dry-run environmental cartography and structured memory. Code Genome tracked source versions and changes but reported zero legacy autonomous mutations. The preserved ContinuityNode build contained no populated runtime memory records.

**Test:** Compare latest-version replacement, ordinary cloning, checkpoint recovery and a capability-preserving lineage archive. Independently evaluate construction, transport, coordination and energy efficiency on matched held-out tasks. A preserved earlier implementation is not automatically a heritable behavioral capability; require a new, separately identifiable execution, a declared inheritance boundary and verified outcomes.
